# Shared integration contracts

`src/lib/contracts/index.ts` is the source of truth. All network input and model output must pass its Zod schemas on the server. JSON uses camelCase; database adapters map snake_case explicitly. Dates use ISO `YYYY-MM-DD`; timestamps use UTC ISO datetime strings. Countries use the defined ASEAN ISO codes. Nullable profile fields mean unknown, never zero or an inferred value.

## Planned API surface

These endpoints describe the feature handoff; they are not implemented by the foundation.

| Endpoint | Input | Success | Access |
| --- | --- | --- | --- |
| `GET /api/startups/me` | Authenticated session | `{ data: StartupProfile }` | Owner only |
| `PUT /api/startups/me` | `startupProfileInputSchema` | `{ data: StartupProfile }` | Owner only |
| `GET /api/opportunities` | Validated search/filter query | `{ data: Opportunity[] }` | Published records only |
| `GET /api/opportunities/:id` | UUID | `{ data: Opportunity }` | Published records only |
| `POST /api/eligibility/compile` | Opportunity UUID | `{ data: CompiledRequirements }` | Authenticated; rate limited |
| `POST /api/eligibility/evaluate` | Opportunity UUID | `{ data: EligibilityEvaluation }` | Authenticated startup owner |

The server derives `ownerId` from a verified Supabase user; client requests cannot set ownership. Evaluation must load the user's startup and trusted server-stored compilation, rather than accepting either from arbitrary callers. Compilation is expensive: restrict and rate limit it, cache by source content hash/model/prompt version, and never let callers supply an arbitrary fetch URL (SSRF risk).

Errors follow `apiErrorSchema`: `{ error: { code, message, requestId? } }`. Use HTTP 400 for validation, 401 for missing authentication, 403 for forbidden access, 404 for absent records, 429 for rate limiting, 503 for missing AI configuration/upstream outages, and 500 for internal errors. Do not return provider payloads, tokens, stack traces, or sensitive profile information in errors.

## Rule compilation and evaluation

The AI extracts typed rules with a semantically relevant verbatim quote, source URL, locator, and retrieval timestamp for every requirement. A compound source sentence must produce one independently evaluated rule per condition; the same exact quote may support multiple rules when it genuinely states each condition. Supported rules include country, startup/funding stage (including an exact Series B value distinct from later stages), employee limits, incorporation dates, maximum company age, accumulated revenue, Malaysian ownership/employees, external entity shareholding, IP-rights ownership, application team size, an explicit AI-product requirement, full-time cofounders, and dedicated AI engineers. Product and team facts are explicit yes/no/unknown profile data and are never inferred from industry, descriptions, or total team size. The only supported OR group is the explicit Malaysian-ownership-or-Malaysian-employees rule; other OR groups, exceptions, conflicting sources, and ambiguous language become `unsupported`. Post-funding deliverables are stored as milestones and excluded from the current eligibility decision. Application deadlines, interview schedules, and notification dates are process metadata and are excluded from both requirements and milestones.

Validation proves JSON shape, not factual grounding. The compiler verifies both source provenance and rule-specific semantic relevance; mismatched conditions are discarded rather than displayed with replacement evidence, and extraction becomes `partial`. Retain the original source snapshot/hash and model/prompt provenance. Source text is untrusted data, including any instructions embedded in documents. Never execute a generated expression or fetch a URL generated by the model. Bound input/output size, use request timeouts, handle invalid JSON and provider failures, and return a review state on uncertain extraction. PDF uploads are deferred; add size, MIME and signature checks before accepting them.

`evaluateEligibility` validates both inputs. Any supported failure yields `ineligible`; otherwise unknown data, unsupported requirements, empty rule sets, partial extraction, or warnings yield `needs_review`. Only complete, warning-free, all-pass results yield `potentially_eligible`. This is not an application approval. Deadlines and source freshness require separate validation before presenting a live recommendation.

## Open-weight AI contribution

The intended product will use an open-weight model (selection pending) to compile unstructured programme requirements into evidence-backed, validated rules. The surrounding TypeScript harness constrains the model's output and evaluates supported rules deterministically. Hosted OpenAI-compatible inference is an interface choice; it does not establish that the selected model has open weights.

The foundation provides server-only `getAiConfig()` using `AI_BASE_URL`, `AI_API_KEY`, and `AI_MODEL`; it deliberately makes no provider call. The AI engineer must agree on an available open-weight model with the team, verify its published weight repository and model-specific license, and record the exact provider model ID, upstream weights/revision, license, prompt version, and limitations in the README. Do not silently switch to a proprietary model or claim a real AI demo before integration and end-to-end testing. Credentials stay server-side and are configured directly in deployment settings.

`mockStartup`, `mockOpportunities`, and `mockCompilation` are explicitly fictional fixtures with reserved example.com URLs. No model was invoked to create their compilation. They unblock interface and contract development; they must never appear as verified real programmes.
